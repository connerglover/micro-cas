# T1.4: Decimal formatter (notes)

Files: `src/printer.py` (only `DECBITS`, `dec10`, `fdec10` so far), `tests/test_dec10.py`.

## Public API (as implemented, DESIGN.md section 12.6)

- `dec10(p, q, nd=10)` `#@L 7`. Takes int `p` and int `q > 0`. Returns the text of `p/q` with
  `nd` significant digits, rounded half-up (ties go away from zero).
  - The notation is chosen on the rounded value. It is scientific when |x| >= 1e10 or
    |x| < 1e-4: `1E10`, `9.9990001E-5`, `-1.428571429E399`. There is no `+`, and the
    mantissa has no trailing zeros. Otherwise the notation is fixed: `0.0001`, `3.142857143`,
    `9999999999`.
  - `0` gives `'0'`. Exact integers within range print without a point: `dec10(1000, 1)` is
    `'1000'`.
  - The function is a leaf. It calls only `str`, `len` and `divmod`, so it makes no Python
    frames.
- `fdec10(x, nd=10)` `#@L 6`. Takes a float and returns `dec10` of its exact binary value,
  through `math.frexp` and a 53-bit integer mantissa. The digits are the same on the device and
  the desktop by construction.
  - `0.0` and `-0.0` give `'0'`.
  - `inf` raises `OverflowError`, and `nan` raises `ValueError`. Both come from `int()`, which
    behaves the same way on MicroPython.
  - Use `fdec10(re, 15)` for FLT text (section 12.4 writes this as `fdec(re, 15)`).
- `DECBITS = 13287`. See the deviation below.

## Deviation from DESIGN.md

- **Huge-integer guard.** `dec10` raises `OverflowError('dec10')` when `p >= 2^13287` or
  `q >= 2^13287`, that is, when either has more than about 4,000 digits. The section 12.6
  sketch has no guard. Section 6.1 says the printer never calls `str()` on an integer of more
  than 4,000 digits, and the sketch calls `len(str(p))`.
  - `p >> DECBITS` costs O(1) for a small int and O(n) for a big one, and keeps no resident
    constant.
  - Nothing is lost: such a rational's text is over `MAXTEXT` anyway (`Done`), and
    `PR.record` turns any exception into "no decimal line".
- **No module-default `#@L` on line 1.** Each def has its own annotation, so T1.7 can choose
  the module default.

## Tests (`tests/test_dec10.py`, 80 tests, about 5 s, none marked slow)

- **Reference.** CPython `decimal` is used with `ROUND_HALF_UP` at precision `nd`. Division and
  `plus` are correctly rounded. The layout rules are written again on their own in `ref_text`.
- **Acceptance:**
  - 20,000 random rationals: general cases, magnitudes near both thresholds, exact ties at
    digit 11 (some scaled so the fraction is not reduced, some nudged just above or below the
    tie), and values that round up to a power of ten.
  - 20,000 random doubles, every bit pattern including subnormals, at `nd = 10` and `nd = 15`.
  - Result: 0 mismatches.
- **Fixed cases.** The section 12.6 examples, and the threshold cases on both sides of 1e10
  and 1e-4, including the rounding carry that changes the notation: `9999999999.5` gives
  `1E10`, and `9.9999999995E-5` gives `0.0001`.
- **Other checks:**
  - `nd` from 1 to 30;
  - 17 digits round-trip through `float()`;
  - every output has a valid shape and its value is correct;
  - rationals of up to about 4,000 digits are formatted exactly;
  - the guard;
  - inf and nan raise.
- **Depth.** Both functions measure at depth 7, which is their declared level. They pass in
  `--strict-depth` too. lint and FRAMELINT are clean (`7: 6 printer.fdec10 > 7 printer.dec10`).
- **Mutation check** (run by hand, outside the repo). These 7 mutants were all caught: tie
  rounding, both thresholds, the carry, the exponent estimate, zero stripping, and mantissa
  precision.

## Notes for downstream tasks

- **T1.7 (printer).** T1.7 owns the rest of `printer.py`. Keep `dec10`, `fdec10` and
  `DECBITS` as they are, or update `test_dec10.py` with them.
  - An integral float prints with no point: `fdec10(3.0, 15) == '3'`. That text re-parses as
    the exact integer 3, not as a FLT. The round trip of section 12.5 therefore needs FLT text
    to carry a float marker: for example, append `.` when the text has neither `.` nor `E`. A
    float like `0.25` re-parses as a FLT anyway (D8). This choice is T1.7's, together with the
    T1.3/T1.5 lexer.
  - The decimal line must still run inside `record`'s `try`, because of `OverflowError` from
    the guard and from inf.
- **T1.3/T1.5 (lexer, `exact()`).**
  - Scientific output uses `E` and a bare negative exponent: `1.5E-5`, `1E10`. The lexer must
    read `E-5` and `E10` as a float exponent (D14).
  - `exact()` can take the 15-digit text from `fdec10(x, 15)` and read it as a rational.
- **T1.1 / section 6.1 (unverified concern).** The design says that `'%x' % n` is linear, so
  the `MAXBITS` and `str()` size estimates use the hex length. On CPython this is true. On
  MicroPython, `mpz_as_str_inpl` probably divides by the base once per output digit for every
  base. That would make hex conversion quadratic, like decimal conversion. `n >> k` is linear
  on both, so a size test by shift avoids the question. This is how `dec10` tests size. Worth a
  CVTEST timing.
